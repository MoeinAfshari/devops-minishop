## Day 47 Challenges

### Challenge 1 - Analyze plan

Suppose you see these phrases when reviewing Plan:
```
+ create

~ update in-place

-/+ destroy and then create replacement
```
#### Task

Eplain for each one:
1. What operation does Terraform intend to perform?
2. When might this operation be dangerous?
3. What should you check before Apply?
4. If Replace is suggested, how do you determine the reason?

Limitation: The answer “I’ll just execute the plan and see what happens” is not acceptable. You need to understand the change plan first.

#### Answer

**`+ create`:** Terraform proposes creating a new resource. I should verify its configuration, dependencies, permissions, cost, and target environment before applying the plan.

**`~ update in-place`:** Terraform proposes updating one or more attributes of an existing resource without replacing it. I should inspect the changed attributes and check for possible servi
ce impact or effects on dependent resources.

**`-/+ destroy and then create replacement`:** Terraform proposes destroying an existing resource and creating a replacement. I should identify the attribute or configuration change that req
uires replacement and assess the impact before applying the plan.

If only the resource address has changed, a `moved` block may prevent an unnecessary destroy-and-create operation. If an attribute requires replacement, a `moved` block will not solve that p
roblem. `prevent_destroy` blocks the destructive plan, while `create_before_destroy` changes the replacement order when the resource allows it.

### Challenge 2 - Input validation

In the Day 47 lab, you have the following Resource:
```
local_file.guarded
```
This Resource should only be created when the input content is not empty.

#### Task

1. Explain how a `precondition` prevents the operation from proceeding when provided with invalid input.
2. Test the empty input scenario using `invalid.tfvars`.
3. Record the actual Terraform output.
4. Explain why the result of `terraform validate` alone is insufficient to prove that this condition has been successfully met.

#### Answer

The `precondition` checks whether `file_content` contains a non-empty value after trimming whitespace.

I tested the empty input using `invalid.tfvars`. Terraform returned the error message defined in the `precondition` block and stopped the plan.

The `status_path` output contains the path of the generated file. I can read it with `terraform output -raw status_path` after the output has been recorded in state.

`terraform validate` checks the configuration's syntax and internal consistency. It does not evaluate this resource precondition using the specific empty value supplied through `invalid.tfvars`; that check occurs when Terraform creates the plan.

### Challenge 3 - Resource protection

In the lab, you have changed the file name and Terraform suggests a replacement instead of a simple Update.
In the same Resource, `prevent_destroy` is enabled.

#### Task

1. Investigate the reason why a replacement is required.
2. Review the plan and record the outcome.
3. Explain why having `prevent_destroy` enabled blocks this operation.
4. Revert the configuration to its original version.
5. Run `terraform fmt -check`, `terraform validate`, and `terraform plan` again.

Constraint: To complete this challenge, do not remove `prevent_destroy`, and do not attempt to force the plan to execute by disabling the protection.

#### Answer

I inspected the plan and found that Terraform rejected the proposed replacement because `prevent_destroy = true` was enabled.

I should not disable the lifecycle protection just to make the plan succeed. First, I need to understand why Terraform requires a replacement.

In this lab, I should restore the original filename, keep `prevent_destroy = true`, and run `terraform fmt -check`, `terraform validate`, and `terraform plan` again.

I should apply changes only if they are necessary, understood, and safe.

### Challenge 4 - The file exists, but it's not in the state

Suppose a file actually exists on disk, but its resource is not visible in Terraform State.

#### Task

Write a safety-check routine to determine:

1. Does the file actually exist?
2. Are you in the correct Terraform directory?
3. Is the resource recorded in the state?
4. What changes does the plan propose under these conditions?
5. What evidence should be gathered before applying any changes?

Constraints for this challenge:
- Do not immediately delete the existing file.
- Do not modify the state to hide discrepancies.
- Verify that the resource in question supports the `import` operation; do not assume it can be imported simply because a file exists.
- Do not run `apply` without fully understanding the actual impact of the plan.

#### Answer

Investigation:
```Bash
git rev-parse --show-toplevel
pwd
cd infra/terraform/local-lab
test -f generated/minishop-lab-status.txt \
  && echo "The file exists." \
  || echo "The file does not exist."
terraform state list
terraform state show module.status_file.local_file.status
terraform plan
```

First, I would verify the repository root, the Terraform root module, and the exact path of the existing file.

I would inspect the file's content and check whether the corresponding resource is present in the current Terraform state. I would also inspect the resource configuration to confirm its `filename` value.

If the resource is declared in the configuration but missing from the state, Terraform may propose creating it. For a `local_file` resource, applying that change can overwrite the existing file with the configured content.

I would review the plan carefully and verify the provider's import support before choosing a recovery method. I would not run `terraform apply`, delete the file, or modify the state until I understood the consequences.
