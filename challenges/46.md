## Day 46 Challenges

### Challenge 1 - Safe Module Refactoring 

Suppose the previous Resource was in the Root Module and you moved it to the Child Module. 
Explain how you would determine that Terraform detected the Resource move, rather than destroying and recreating it. 
Expected output:
- Related section plan
- Previous resource address
- New resource address
- Verification method

Success criterion: Correctly detecting address changes and preventing unwanted operations.

#### Answer

When I use a moved block, I expect the plan shows me a replacement part, no a destroy and create (-/+). I use from a moved block in the `main.tf` of root module like:
```
moved {
  from = local_file.minishop_status
  to = module.status_file.local_file.status
}
```
Then I validate it: 
```Bash
terraform fmt -recursive -check
terraform validate
terraform plan -out=/tmp/day46.tfplan
terraform show /tmp/day46.tfplan
terraform apply /tmp/day46.tfplan
```
For verfication after applying: 
```Bash
terraform state list
terraform state show module.status_file.local_file.status
terraform output
terraform show
cat generated/minishop-lab-status.txt
```
Note:
- Resource address change: It manages with moved block.
- Resource attribute change: I may cause an update or even a replacement.

### Challenge 2 - path.root vs path.module

Following the refactoring, files were created within a subdirectory inside the child module; they should instead be located in the original `MiniShop` path.
This explains the likely cause and corrects the configuration.
Desired outcome: Clarifies the distinction between the two paths and prevents the file location from being altered unintentionally.

#### Answer

The problem probably back to the defined path in the `main.tf`. I should convert `path.module` to `path.root` in the filename address.
`path.root` returns to the root directory while `path.module` returns the filesystem path of the module in which the expression is evaluated. It doesn't simply return the current terminal directory.

#### Challenge 3 - Unexpected Replacement

Following a resource migration, the plan includes a "destroy" and a "create" operation. 
Before applying, review the items in order of priority. 
Expected points:
- State
- Resource address
- moved block
- filename
- content
- file_permission

Success criterion: Identifying the probable cause without hasty implementation of the Plan.

##### Answer

##### Probe cause

- The moved block absences.
- The from or to address is incorrect. 
- The old resource no longer exists in the State. 
- The filename value has changed. 
- One of the attributes requires replacement according to the Schema for the Provider.

##### Investigation

1. Check the plan:
```Bash
terraform show /tmp/day46.tfplan
```
2. Check the state:
```Bash
terraform state list
terraform state show local_file.minishop_status
```
3. Check configuration & Migration:
- Read `main.tf` in the Root & Child Module.
- Match the form and to adresses with the state.
- Compare the values of filename and content.
4. Check the actual file:
```Bash
stat generated/minishop-lab-status.txt
cat generated/minishop-lab-status.txt
```
5. Check output:
```Bash
terraform output
```
Note: The presence of `Destroy` and `Create` in the Plan alone does not mean that the block is not moved; you must specify whether this operation is due to an address change or an attribute change.

#### Challenge 4 - Terraform Repository Hygiene

You want to make sure that sensitive and temporary Terraform files are not pushed into Git. 
Write and explain the appropriate commands:
- What is the difference between an Ignored file and a Tracked file? 
- What is the difference between .terraform/ and .terraform.lock.hcl? 
- If a file is already Tracked, is adding it to .gitignore enough to remove it from Git?

Success criterion: Checking the Git status and correctly identifying files that should not be committed.

##### Answer 

Check ignored files & directories:
- `cd "$(git rev-parse --show-toplevel)"`
- `git status --short`
- `cat .gitignore`
For example about the `terraform.tfstate` file:
```Bash
git check-ignore -v terraform.tfstate
git ls-files terraform.tfstate
git status --short
```

- Ignored file ignores from the Git and so it doesn't track while tracked file tracks with Git and its changes need to stage & commit.
- `.terraform/` includes internal terraform data, downloaded working directories and provider files while `.terraform.lock.hcl` is a lock file and it includes selected versions and checksums of providers.
- No. I should remove the file from git cached too. for this: git rm --cached file | git rm -r --cached folder and then add the file/directory in the .gitignore file.
