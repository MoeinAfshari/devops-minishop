## Day 45 Challenges 

### Challenge 1 - State Inspection

Find a real resource address with `terraform state list` and check it with `terraform state show`. Hold the ouput of each command and explain the difference between them.

#### Answer

`terraform state list` just shows list of resource addresses while `terraform state show local_file.minishop_status` returns a lot of data about the resource state like its content, its path address, its id, ...
| Command | Purpose |
| :-----: | :-----: |
| `terraform state list` | Lists resource addresses in state. |
| `terraform state show ADDRESS` | Inspects one resource in state. |
| `terraform show` | Displays the current state or a saved plan, depending on the input. |
| `terraform plan` | Calculates proposed changes by comparing configuration, state, and refreshed resource information. |

### Challenge 2 - Resource Address

Suppose a resource name is changed in the configuration. Explain why should we review the plan and what signs might indicate deletion and recreation?

#### Answer

A resource name change does not always need to destroy and recreate the actual resource.
You can tell Terraform to preserve the resource's identify using a `moved` block:
Change `main.tf` to:
```hcl
locals {
  status_content = join("\n", [
    "Application: ${var.project_name}",
    "Environment: ${var.environment_name}",
    "Purpose: Terraform local lab only"
  ])
}

resource "local_file" "minishop_lab" {
  filename        = "${path.module}/generated/minishop-lab-status.txt"
  content         = "${local.status_content}\n"
  file_permission = "0644"
}

moved {
  from = local_file.minishop_status
  to = local_file.minishop_lab
}
```
Change `outputs.tf` to:
```hcl
output "generated_file_path" {
description = "Path to the generated MiniShop lab file."
  value       = local_file.minishop_lab.filename
}

output "environment_name" {
  description = "Environment selected for the local lab."
  value       = var.environment_name
}
```
Now:
```Bash
terraform plan
```
You should then inspect the plan to check that Terraform recognizes the move. If other resource attributes also changed, replacement may still be necessary.

Remember: changing a Terraform resource's label is different from changing the actual file's path or content.

### Challenge 3 - Drift Detection

Suppose you manually remove:
```Plain text
generated/minishop-lab-status.txt
```
But the configuration still declares that the file should exist.
Review the plan and explain the result with evidence. If didn't run, record the reason.

#### Answer

A normal plan:
```Bash
terraform plan
```
will generally detect that the managed file is missing and propose recreating it.
By contrast:
```Bash
terraform apply -refresh-only
```
previews changes to Terraform's recorded state to reflect what it finds in the real environment. If the provider detects that the file is missing, Terraform may propose removing its resource entry from state.

Applying that refresh-only plan:
```Bash
terraform apply -refresh-only
```
does not recreate the file, nor does it delete the already-missing file. Its purpose is to update the recorded state, not to reconcile the infrastructure with the desired configuration.

### Challenge 4 - Git Safety

Examine the Git state and explain why `terraform.tfstate`, the actual `.tfvars` file, and `.terraform.lock.hcl` should be managed differently.

#### Answer

| File | What it contains | Git treatment |
| :--: | :--------------: | :-----------: |
| `terraform.tfstate` | State information about managed resources; it can contain sensitive values. | Keep out of Git. |
| `terraform.tfvars` or `dev.tfvars` | Input variable values, which may include secrets. | Ignore sensitive, environment-specific files; commit only when the contents are appropriate for sharing. |
| `.terraform.lock.hcl` | Selected provider versions and package checksums. | Normally commit it to Git. |

A good practical is:
```Bash
git status
git check-ignore -v terraform.tfstate dev.tfvars
git ls-files '*.tfstate' '*.tfvars'
```
