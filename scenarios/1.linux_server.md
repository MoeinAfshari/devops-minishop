## Production Scenario

### Secnario 1 - The server is down

Suppose you get a call at 3 a.m. that the store server is down. The first thing you do is not restart the services. First you need to gather information.
Question: If you are only allowed to run five commands to check the status of the system, choose those five commands and write down the reason for choosing each one.

#### Answer

- The first DevOps Principle: Don't change the system before understanding the problem.
1. `top` for checking whole status
2. `free -h` for get ram status
3. `df -h` for get disk status
4. `ps aux --sort=-%mem | head` | `ps aux --sort=-%cpu | head` for checking that what process uses resources
5. `journalctl -xe` for checking Logs
- A good DevOps: Observe -> Analyze -> Act -> Hope

### Scenario 2 - Backup server by cron

A Backup script is run every night with Cron, but no backup files were created today.
You are only allowed to run 5 commands.
1. What commands do you run?
2. What information does each command give you?
3. At what point do you decide whether the problem is with Cron or the script itself?

#### Answer

1. `crontab -l` -> I check the crontab with -l option and if find a wrong thing, fix it with -e option
2. `grep CRON /var/log/syslog` | `grep CRON /var/log/cron` -> I wanna figure out that cron ran job or not
3. `bash -n script.sh` (checks syntax) -> `less script.sh` -> I check the script to verify that there are no syntax or logical errors. If I found an error, debug it. -> `bash -x script.sh` (Debugger tool)
4. `ls -l script.sh` | `stat script.sh` -> Check the script permissions and dependency files and directories permissions.
5. `journalctl -u cron` | `journalctl -u crond` -> Check the cron logs. I try to find problem in the cron logs.
6. `journalctl --since "02:00" --until "02:10"` -> Check all logs in the Backup time frame in the end.

### Scenario 3 - Permission denied

One of co-workers say: "I run the script but I get permission denied!"
You are only allowed run 5 commands.
Write:
1. What commands do you run?
2. Why do you choose each one?
3. At what point do you decide whether the problem is with Permissions, the file owner, or the file path?

#### Answer

1. `whoami` | `echo "$USER"` -> I verify which user is executing the script because the current user may not have permission to execute or access the file.
2. `id` -> I check the groups that the user is in them.
3. `stat script.sh` -> I check the permissions of file, owner, group, ...
4. `namei -l /path/to/script.sh` -> This command is really popular Linux tool for debug permissions. (If a directory doesn't have Execute Permission, I get permission denied)
5. `journalctl -xe` -> After run script and get permission denied, check the last logs.

### Scenario 4 - Permission denied

User `developer` can't edit `/opt/app/config.yaml`
What do you do with 5 commands?

#### Answer

1. `whoami` | `echo $USER` -> I verify that I'm logged in as the expected user before troubleshooting the issue.
2. `id` -> I wanna check my groups.
3. `stat /opt/app/config.yaml` -> Check the permissions, Owner, Group, Mode, ACL, Timestamps.
4. `namei -l /opt/app/config.yaml` -> Check the path permissions.
**Note**: Based of the output of `stat` and `namei`, I determine whether the problem is caused by the file owner, group membership, file permission, or directory permissions. I only make changes after identifying the root cause.
5. `journalctl -xe` -> Check logs -> if the config.yaml is for a unique service or app: `journalctl -u nginx` | `journalctl -u app.service`.
